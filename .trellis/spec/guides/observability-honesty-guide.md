# Observability Honesty Guide

监控/指标类功能的思考清单。核心问题：**这个指标代表的东西，和用户真正关心的事情，是同一件事吗？**

## When to Use

- 做任何"监控 / 告警 / 健康检查 / 质量评分"功能前
- 给已有指标加阈值、加告警、上颜色（红/黄/绿）前
- 用户说"想看看 X 正不正常"时

## The Checklist

### 1. 指标测的是什么？用户关心的是什么？

写下两句话，对比：

- 指标：「ICMP 丢包率」
- 用户关心：「我的网能不能用」

**如果两句不是一回事，中间必须有翻译层，不能直接把指标当结论。**

真实案例（9Router net-monitor）：ICMP 丢包 30%，但 TCP 443 是 10/10、HTTPS 10/10、真实网站 9/9 全通。直接显示「丢包 100%」是假警报。ICMP 是低优先级协议，运营商普遍限速 —— 这是**策略**，不是**故障**。

### 2. 这个指标会怎样失败？

| 失败模式 | 例子 |
|---|---|
| **假阳性**（没事报有事） | ICMP 被限速 → 报"网络故障" |
| **假阴性**（有事报没事） | 只测 TCP，代理挂了但直连正常 → 测不出来 |
| **指标被中间设备改写** | DNS 劫持：`.invalid` 保留域名被解析到 `198.18.0.99` |

**假阳性比假阴性更能杀死一个监控功能** —— 用户被吵三次就不看了，之后真的出事也不会注意。

### 3. 有没有独立的第二信源可以交叉验证？

单一指标容易被中间设备或策略欺骗。**用不同层次的探测交叉验证**：

```
ICMP 失败 + TCP 成功  →  ICMP 被过滤（非故障）
ICMP 成功 + DNS 失败  →  DNS 配置问题
全部失败 + 路由还在   →  上游/网关问题
全部失败 + 路由没了   →  本机网络问题
```

单一指标只能说"我看到什么"，交叉验证才能说"是什么问题"。

ClinePass channel attribution follows the same rule: request details distinguish
`observed` actual provider from `Unverified`; HTTP 200 and the requested pin are
not evidence that the desired channel served the call.

### 4. 阈值是拍脑袋还是有依据？

- 绝对阈值（延迟 < 100ms）在不同网络下意义完全不同（家里宽带 vs 4G vs 卫星）
- 相对阈值（比自己的基线差 N 倍）通常更可靠
- **但相对阈值需要基线** —— 刚开始没有历史数据时怎么办？宁可先不告警

### 5. 会不会天天喊狼来了？

- 单次失败就告警 → 会。要**连续 N 轮同向**才升级
- 证据不足时应该明确说"无法判定"，**不是**默认报"未知故障"
- 恢复也要对称：故障消失后要能回到正常，不能卡在告警态

## Anti-Patterns

| 反模式 | 为什么错 |
|---|---|
| 把原始指标直接当结论展示 | 指标 ≠ 用户关心的事 |
| 单次失败就变色/告警 | 瞬时抖动是常态，会淹没真信号 |
| 只测一层就下结论 | 中间设备可以只拦一层 |
| 证据不足时猜一个原因 | 把用户引向错误方向比不说是更糟的服务 |
| 所有异常都用同一个红色 | 用户无法区分"网断了"和"ICMP 被限速" |
